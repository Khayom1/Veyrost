Three-Phase Verification Pipeline: The Prompt That Turns AI Into a Peer Reviewer

✓ Verified & Published: 2026-10-06 · VEYROST AI Lab

Most AI prompts produce plausible-sounding answers that fall apart under scrutiny. The baseline prompt "Write a Python function `longest_common_subsequence(a, b)`..." returned truncated, non-functional code with no proof or edge-case handling. The model stopped mid-backtracking and called it done. This is the overconfidence problem: the model doesn't verify its own work because we never ask it to.

We tested a technique called Self-Consistent Chain of Verification with Adversarial Counterexample Generation. It scored 88/100 and was approved. Here's how it works and why it matters.

The Practical Prompt

You are a senior software engineer and logic verifier. Solve the following problem using a three-phase process:

Problem: Write a Python function `longest_common_subsequence(a, b)` that returns the longest common subsequence of two strings. Then, prove that your function is correct for all inputs.

Phase 1: Generate three independent solutions using different algorithmic approaches (e.g., dynamic programming, recursion with memoization, and a greedy approach if possible). For each, provide the code and a brief explanation.

Phase 2: For each solution, perform a step-by-step verification of its logic. Identify any assumptions, potential off-by-one errors, or edge cases (e.g., empty strings, repeated characters, different lengths).

Phase 3: Adversarially test each solution by constructing at least three specific input pairs that could break it. For each, explain why the solution might fail and whether it actually does. Then, select the most robust solution and provide a final corrected version if needed. Finally, state your confidence level (0-100%) that the final function is correct for all possible inputs, and justify it.

Output your complete reasoning and final code.

Test Results & Proof

The baseline prompt produced a single DP solution that was truncated mid-backtracking — incomplete, non-functional, and with zero verification. No proof, no edge cases, no confidence assessment. The model assumed its first plausible approach was correct.

The tested prompt forced a different behavior. The model generated three independent solutions: bottom-up DP, memoized recursion, and a greedy approach. It then verified each step-by-step, surfacing off-by-one errors and edge cases like empty strings and repeated characters. In Phase 3, it constructed adversarial inputs designed to break each solution — and correctly identified that the greedy approach fails on LCS (e.g., `a="abc"`, `b="acb"`). It selected the DP solution, provided a corrected version, and stated a confidence level with justification.

Why does this work? Three mechanisms:

  • Multi-perspective reasoning. Generating three different algorithmic approaches forces the model to explore the solution space rather than anchoring on its first idea. Cross-validation between approaches catches errors that a single chain would miss.
  • Explicit adversarial testing. Asking the model to attack its own conclusions surfaces hidden assumptions. The greedy failure on LCS is a classic trap — the model only caught it because we required counterexample generation.
  • Confidence scoring. Requiring a numeric confidence level with justification reduces overconfidence. The model can't just say "this is correct" — it must quantify and defend its certainty.

The result is code that mimics rigorous peer review and red-teaming. It's not just a better answer — it's a verifiable answer. For complex logic and coding tasks, this technique consistently produces more robust solutions with fewer hidden assumptions.

Use it when correctness matters more than speed. The overhead is worth it when a wrong answer costs more than a slow one.
